Contexte & solution

Rendre l'info-trafic 107.7
accessible aux conducteurs étrangers.

Problème

La radio autoroutière 107.7 diffuse les alertes trafic (accidents, bouchons, fermetures) uniquement en français. Pour un conducteur étranger, cette information peut être difficile à comprendre au moment où elle est utile.

Solution

Une plateforme qui prend un audio français, le transcrit, le traduit dans la langue cible, et restitue la traduction en audio synthétisé. 

# Chaîne d'inférence
Audio FR → STT → LLM → TTS → Audio langue cible

Le défi n'est pas d'appeler trois modèles, c'est d'industrialiser la chaîne : évaluation, orchestration, déploiement, observabilité, sécurité. C'est un projet LLMOps, pas seulement une application IA.

Ce que la plateforme apporte

Un socle réutilisable,
déployé en production.

Cas d'usage principal

  • Upload audio FR — MP3 / WAV ou enregistrement micro direct
  • Transcription automatique (Faster-Whisper large-v3)
  • Traduction vers EN, ES, DE, IT, UK
  • Restitution vocale synthétisée (Voxtral · MMS-TTS)
  • Latence et coût — ordres de grandeur observés en production (à confirmer par la campagne de rebenchmark)

Valeur apportée

  • Sécurité routière — prévention accidents secondaires
  • Multilingue à coût maîtrisé — 5 langues cibles
  • Architecture réutilisable — même socle pour d'autres cas d'usage audio
  • Observable — chaque requête tracée, coût suivi en temps réel

Extensions du socle : Meeting Recorder · Live speech-to-speech

Deux cas d'usage

Le socle,

Use case 1 — cœur du projet

Information trafic multilingue

Flash radio 107.7 ou enregistrement audio du conducteur → transcription → traduction → synthèse vocale dans la langue de l'usager.

→ C'est ce cas qui a piloté la conception du pipeline complet.

Use case 2 — réutilisation du socle

Compte-rendu de réunion multilingue

Enregistrement micro long en réunion → transcription continue chunked → génération d'un résumé structuré via LLM (synthétique, détaillé, actions).

💡 Démontre la réutilisabilité du socle sur un nouveau domaine (piste SaaS).

Extension supplémentaire : Live speech-to-speech via WebRTC direct navigateur ↔ OpenAI Realtime.

Architecture

14 conteneurs Docker,
6 microservices FastAPI.

14 conteneurs Docker — 6 microservices FastAPI (Gateway, Pipeline, STT, LLM, TTS, Watcher) + Frontend Next.js + MLflow + Prometheus + Grafana + 3 conteneurs Airflow (Scheduler, Webserver, Postgres) + Airflow-init (éphémère). Nginx sur le host, Langfuse en cloud externe. Le service LLM route vers GROQ, OpenAI et Anthropic via LiteLLM. Meeting appelle directement STT et LLM. Live utilise la Gateway uniquement pour obtenir le token éphémère OpenAI Realtime, puis WebRTC direct navigateur ↔ OpenAI. Survole chaque bloc pour voir les détails.

Parcours de la donnée

Deux flux,
deux parcours différents.

Même stack, deux parcours très différents. Le Flux A est synchrone bloquant (user attend son audio). Le Flux B est asynchrone continu (background, alimente le dashboard admin). Le Watcher n'appelle ni le Pipeline ni le service STT — il a son propre Whisper embarqué et parle direct au LLM.

Orchestration d'une requête

Pipeline LangChain LCEL,
trois niveaux d'orchestration.

Chaîne STT → LLM → TTS

LCEL compose les trois étapes avec l'opérateur |. Chaque étape est un Runnable typé, testable et instrumenté. Le tracing Langfuse est natif. 

# LCEL — 3 étapes composées
pipeline = (
    RunnableLambda(_stt_step)
    | RunnableLambda(_llm_step)
    | RunnableLambda(_tts_step)
)

3 niveaux d'orchestration

  • Docker Compose — cycle de vie des 14 conteneurs (infrastructure)
  • LangChain LCEL — chaîne d'une requête IA (temps réel)
  • Airflow — traitements batch planifiés (nightly / weekly)

Airflow n'intervient pas dans le chemin temps réel de l'utilisateur. Séparation stricte des responsabilités.

Monitoring infrastructure

Prometheus scrape /metrics sur les 6 services FastAPI toutes les 15 s. Grafana affiche latence p50/p95/p99, throughput, erreurs 4xx/5xx, coût cumulé. Dashboards versionnés en Git.

Sécurité, 3 couches

  • Réseau — un seul port public (443), 14 conteneurs bindés 127.0.0.1, HTTPS Let's Encrypt
  • Auth applicative — JWT HS256 15 min + refresh 7j rotatif SHA-256, bcrypt password, 25 tests unitaires
  • LLM — prompt-guard : pre-check regex FR/EN, séparation structurée <user_text>, post-check ratio + leak detection (inspiré OWASP LLM01)

Limites assumées

  • Golden dataset limité à 7 audios
  • GPT-4o mini pas encore rebenchmarké sur protocole identique
  • Gateway pas encore centralisée à 100 % (frontend a des accès directs)
  • Nightly Airflow : disponibilité + latence, BLEU/METEOR non intégrés

Priorités +3 mois

  • Golden dataset 7 → 50+ audios
  • Benchmark GPT-4o mini sur protocole identique
  • BLEU/METEOR + alerting Slack dans le DAG nightly
  • Centralisation complète Gateway (durcissement)
  • Speaker diarization pour Meeting Recorder

La priorité n'est pas d'ajouter davantage de technologies, mais de renforcer la robustesse de l'évaluation et de fermer complètement la boucle LLMOps.
